# Final benchmark protocol research

Date: 2026-08-12

## Verdict

**Protocol readiness: conditional. Confidence: high.** The repository has the correct runner family and a defensible immutable DeepSWE v1.1 catalog snapshot, but its present runs are mechanism/product evaluations. They are not equivalent to either the published DeepSWE leaderboard experiment or the current Terminal-Bench 2.1 submission protocol.

## DeepSWE v1.1 identity and lifecycle

- The official DeepSWE corpus contains **113 tasks** across TypeScript, Go, Python, JavaScript, and Rust. v1.1 retains those same tasks while changing execution and grading. The repository pin `435ee89ec2f2e2289f33b0da4f992f0b7b7266b9` resolves to an official 113-task snapshot and is therefore a valid immutable **catalog-compatible snapshot**. It is not a tagged v1.1 release: the official repository exposes no v1.1 Git tag, so an upstream canonical v1.1 tag or catalog digest is **unavailable**. [DeepSWE README](https://github.com/datacurve-ai/deep-swe/blob/435ee89ec2f2e2289f33b0da4f992f0b7b7266b9/README.md), [v1.1 release note](https://deepswe.datacurve.ai/blog/deepswe-v1-1), [official tags](https://github.com/datacurve-ai/deep-swe/tags)
- v1.1 grades only committed work: the agent works in its isolated checkout and commits; each task's `[[verifier.collect]]` hook produces `model.patch`; Pier collects that artifact; a fresh verifier environment applies it and runs the functional verifier. Uncommitted edits are therefore outside the graded patch. The task instructions themselves request a final commit, and a missing/failed collect artifact becomes an empty submission. [DeepSWE task-format contract](https://github.com/datacurve-ai/deep-swe/blob/435ee89ec2f2e2289f33b0da4f992f0b7b7266b9/README.md#task-format), [representative instruction](https://github.com/datacurve-ai/deep-swe/blob/435ee89ec2f2e2289f33b0da4f992f0b7b7266b9/tasks/abs-module-cache-flags/instruction.md), [representative task configuration](https://github.com/datacurve-ai/deep-swe/blob/435ee89ec2f2e2289f33b0da4f992f0b7b7266b9/tasks/abs-module-cache-flags/task.toml), [Pier lifecycle](https://github.com/datacurve-ai/pier/blob/v0.3.1/src/pier/trial/trial.py#L736-L758), [Pier collect-hook implementation](https://github.com/datacurve-ai/pier/blob/v0.3.1/src/pier/trial/trial.py#L848-L891)
- `datacurve-pier==0.3.1` is the correct Mini-SWE-compatible execution path. DeepSWE explicitly requires Pier newer than 0.3.0, its quickstart uses Pier with `mini-swe-agent`, Pier 0.3.1 declares Harbor-task and Mini-SWE support, and Pier exposes `--agent-import-path` for a custom compatible agent. The repository's thin Pier adapter is therefore legitimate for testing GroundTruth while retaining the v1.1 collect/separate-verifier lifecycle. [DeepSWE quickstart](https://github.com/datacurve-ai/deep-swe/blob/435ee89ec2f2e2289f33b0da4f992f0b7b7266b9/README.md#quickstart), [Pier v0.3.1 README](https://github.com/datacurve-ai/pier/tree/v0.3.1), [custom-agent option](https://github.com/datacurve-ai/pier/blob/v0.3.1/src/pier/cli/jobs.py#L316-L324), [PyPI release](https://pypi.org/project/datacurve-pier/0.3.1/)

## What the DeepSWE result may claim

The public DeepSWE paper's comparable leaderboard experiment uses all 113 tasks, holds the unmodified Mini-SWE prompt and loop fixed at commit `adfe20233d456104c38c3129161b54f0fd39f2c7`, uses a 9,000-second wall-clock limit with no step or cost cap, and draws about four rollouts per task/configuration. It explicitly calls a ten-task harness comparison directional rather than a product-harness ranking. [Harness](https://arxiv.org/html/2607.07946#S5.SS2), [metrics](https://arxiv.org/html/2607.07946#S5.SS3), [sampling](https://arxiv.org/html/2607.07946#S5.SS4), [scope limitation](https://arxiv.org/html/2607.07946#S8)

The current [DeepSWE workflow](../.github/workflows/deepswe_miniswe_central.yml) defaults to 10 tasks, one rollout, a custom Mini-SWE-derived agent loop, a 300-call cap, and a 5,400-second execution budget. Consequently:

- a matched GT-off/GT-on run can support a **GroundTruth mechanism or product claim** if both arms freeze the same task IDs, snapshot, model/provider, prompt boundary, adapter, limits, retry policy, and verifier lifecycle;
- it cannot be reported as a DeepSWE leaderboard-equivalent score;
- the workflow phrase "DeepSWE parity is 300" is **not verified by the inspected official v1.1 sources**. The published experiment instead states that it used no step cap. Exact public v1.1 leaderboard acceptance rules beyond the published materials are **unavailable**.

## Terminal-Bench version and readiness boundary

The repository does not currently state one final Terminal-Bench target. [FINAL_BENCHMARK_CONTRACT.md](../FINAL_BENCHMARK_CONTRACT.md) and the executable [central workflow](../.github/workflows/tb2_miniswe_central.yml) specify **Terminal-Bench 2.0** (`terminal-bench@2.0`), while [FINAL_BENCHMARK_READINESS.md](../FINAL_BENCHMARK_READINESS.md) and [FINAL_EXECUTION_PLAN.md](../FINAL_EXECUTION_PLAN.md) specify **Terminal-Bench 2.1**. That version conflict must be resolved before freezing a final result.

- For a version-specific legacy/product comparison, the repository's TB2.0 pin `2fd12b88aafdd04a52c298e3940bcb189f9766d6` and expected 89 tasks match the official TB2.0 repository and Harbor dataset name. Such a result must remain labeled TB2.0. [Official TB2.0 repository](https://github.com/harbor-framework/terminal-bench-2/tree/2fd12b88aafdd04a52c298e3940bcb189f9766d6), [TB2.0 Harbor invocation](https://github.com/harbor-framework/terminal-bench-2/blob/2fd12b88aafdd04a52c298e3940bcb189f9766d6/README.md#getting-started)
- The current benchmark line is TB2.1. Its official release changes 28 of the 89 TB2.0 tasks because of dependency drift, resource mismatches, and misspecification. Results across 2.0 and 2.1 are therefore not interchangeable. [Official TB2.1 release](https://www.tbench.ai/news/terminal-bench-2-1)
- A leaderboard-grade TB2.1 run must use the unmodified dataset `terminal-bench/terminal-bench-2-1@sha256:7d7bdc1cbedad549fc1140404bd4dc45e5fd0ea7c4186773687d177ad3a0699a`, all 89 tasks, at least five trials per task, default timeout/resource settings with no agent or verifier timeout overrides, public Harbor uploads, canonical per-task digests, and auditable trajectories for rewarded trials. Errored trials score zero. [Canonical dataset identity](https://github.com/harbor-framework/terminal-bench-2-1/blob/main/leaderboard/src/leaderboard/core/hub.py#L19-L24), [submission rules](https://github.com/harbor-framework/terminal-bench-2-1/blob/main/leaderboard/SUBMIT.md#before-you-start), [enforced checks](https://github.com/harbor-framework/terminal-bench-2-1/blob/main/leaderboard/src/leaderboard/ci/static_analysis.py#L39-L66)
- The current central workflow defaults to a 20-task TB2.0 subset, one trial, a 100-call cap, and an explicit agent-timeout multiplier. It is therefore a mechanism diagnostic, even if its verifier result is valid. Clearing the subset alone would not make it TB2.1 leaderboard-grade. Moreover, official TB2.1 community submissions are currently closed; only maintainer-run submissions are accepted. [Submission status](https://github.com/harbor-framework/terminal-bench-2-1/blob/main/leaderboard/SUBMIT.md#submitting-to-the-leaderboard)

## Final claim boundary

**Mechanism diagnostic:** bounded or single-rollout matched A/B evidence may establish integration integrity, absence of regressions on that cohort, and a directional effect of GT under the frozen custom scaffold. It must report task-level outcomes and full resource accounting, including the bootstrap overhead.

**Leaderboard-grade evidence:** requires the benchmark owner's exact dataset, full coverage, sampling, limits, scoring, artifact, and audit protocol. The current workflows do not meet that threshold. A valid verifier reward from Pier or Harbor proves task outcome under the executed protocol; it does not by itself convert a custom, capped, undersampled experiment into leaderboard evidence.
